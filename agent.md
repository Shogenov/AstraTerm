# Правила работы над AstraTerm

## Постоянное пожелание пользователя

**Любое изменение общего поведения, функций и дизайна по умолчанию реализовать и проверить одновременно в Linux и Windows.** Не заканчивать задачу после изменения только одной реализации. Исключения: пользователь явно выбрал одну платформу либо исправление относится исключительно к механизму ОС; тогда проверить общий контракт и объяснить границу. Это правило имеет приоритет над прежним раздельным развитием портов.

## Минимальный вход в задачу

1. Прочитать [docs/CONTEXT.md](docs/CONTEXT.md): ограничения, карта кода и команды.
2. Найти нужный сценарий в [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md); читать только соответствующие функции через `rg`.
3. При изменении архитектуры читать нужный раздел [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
4. Точные правила затрагиваемого механизма — [docs/ENGINEERING_RULES.md](docs/ENGINEERING_RULES.md). Для PTY/MultiExec, SSH/секретов и записи файлов эти разделы обязательны.
5. [docs/FEATURES.md](docs/FEATURES.md) — реализованные функции; [docs/ROADMAP.md](docs/ROADMAP.md) — оставшееся. Не читать всю историю выпусков ради небольшой правки и не считать план реализацией.

## Общий контракт

- `shared/product.json` — единственный источник версии релиза, схемы данных, протоколов, портов и общих SSH-полей.
- `shared/contracts/*.json` — одинаковые поведенческие сценарии Python и JavaScript. Общую правку сопровождать одним новым сценарием, где это применимо, и проверкой обеих реализаций.
- `astraterm/_shared.py`, `windows/src/shared.cjs`, `windows/src/tab-contracts.cjs`, `windows/src/host-stats-contract.cjs` — сгенерированные файлы. Не редактировать вручную; запускать `python tools/sync_shared.py`.
- `windows/package.json`/lockfile — зеркала общей версии. Новый релиз: `python tools/sync_shared.py --version X.Y.Z`. Версия приложения и версия пользовательской JSON-схемы — разные сущности.
- GTK/Python 3.5 и Electron/ConPTY остаются отдельными адаптерами. Не переносить Electron в Astra 1.6 и не заменять полноценный терминал текстовым полем.
- Данные пользователя и внешние клиенты платформенные. Общие правила и совместимость JSON — единые; равный номер релиза не означает поддержку всех протоколов на обеих ОС.

## Обязательные границы

- Только человеческий ввод отмеченного источника MultiExec рассылается отмеченным работающим получателям. Макросы, ответы терминала, поля форм остаются локальными; reconnect/exit сбрасывают выбор. Не терять PTY/историю при перемещении панелей.
- Проверять ключи серверов и обязательные SSH-маршруты. Секреты не записывать в репозиторий, экспорт, argv, журналы. Профили ключей — только метаданные; пользовательские ключи/агент не использовать для автотестов.
- Импорт паролей разрешён пользователем только в отдельное хранилище под мастер-паролем. `sessions.json` и экспорт остаются без секретов. Правила и границы: [docs/IMPORTS.md](docs/IMPORTS.md); не сохранять открытые пароли вместо шифрованного хранилища.
- Файловые операции привязаны к исходному соединению/поколению; смена фокуса не меняет получателя. Ревизии, временные файлы, откат и предупреждения резервных копий обязательны. Не превращать Delete в рекурсивный.
- В Linux использовать Python 3.5.3/GTK 3.22/VTE 0.46 и `/usr/bin/python3.5`; не менять системные alternatives или ОС. В Windows сохранять sandbox/context isolation и ограниченный IPC.
- Сборка Linux выполняется в Linux; Windows — в Windows. Не выдавать исходный архив за бинарную сборку и успешную упаковку за проверку GUI.

## Завершение задачи

Обновить код обеих платформ, контракты и относящиеся к задаче документы. Выполнить подходящие проверки в каждой целевой среде; честно указать непроверенное. Общая сборка: `build-all.ps1` или `tools/build.py`; подробности — [docs/BUILD.md](docs/BUILD.md). Не пересобирать тяжёлые бинарники ради документации; не повторять прошедшие проверки без новых изменений/рисков.

При существенном новом решении обновить соответствующий раздел архитектуры и короткий `CONTEXT.md`, а не добавлять историю чата. Не сохранять в этих документах IP, логины, пароли и пути к реальным пользовательским ключам.
